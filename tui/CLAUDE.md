# CLAUDE.md - `sotto` terminal client (`tui/`)

> Premium headless Rust + ratatui client for the Sotto platform. Standalone crate **outside** the npm workspaces. Talks to a Sotto server's `/api/v1` over HTTP only — it holds no business logic, only presentation, audio, and the typed client. Crate is `sotto-tui` on crates.io; the installed binary is `sotto`.

## Build & Test

```bash
cd tui
cargo build
cargo test                       # ~166 tests, all hermetic (no network, no device)
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

Never use npm here. This crate is not a workspace member; `npm run ci` does not cover it. Edition 2024, MSRV pinned in `Cargo.toml`.

## Architecture

- `main.rs` — clap entry. Subcommands `login` / `switch` / `accounts` / `logout` / `whoami`; no subcommand launches the TUI.
- `app/mod.rs` — the `App`: owns `Arc<dyn Api>`, dispatches async work on a tokio mpsc channel, and applies results back on the main loop. Each result is tagged with a monotonic `request_gen`; a stale generation is dropped so a late/cancelled response never mutates current state.
- `app/state.rs` — **pure** state machine (no I/O). This is where logic lives and where most tests are. Keep it side-effect-free so it stays unit-testable.
- `app/ui.rs` — ratatui rendering only. `app/class.rs`, `app/exam.rs`, `app/onboard.rs`, `app/ask.rs`, `app/overlay.rs` — per-flow state + view. `class.rs`/`exam.rs` share a `FlowKind` seam.
- `api.rs` — the `Api` trait (the async seam) and `SottoClient`, its progenitor-backed impl. `action.rs` / `event.rs` / `tui.rs` — action enum, crossterm event stream, terminal setup/teardown.
- `audio/playback.rs` (rodio) and `audio/record.rs` (cpal capture → `hound` WAV). `config.rs`, `auth.rs`, `theme.rs`, `components/`.

## Contract codegen — do not hand-edit generated code

The typed client is generated by `progenitor::generate_api!` from a **vendored** spec `tui/openapi.codegen.json`, which is byte-for-byte identical to `packages/shared/openapi.codegen.json`. Both are produced by `npm run gen:openapi` (run from the repo root) out of the Zod schemas in `packages/shared`. The vendored copy exists so the crate builds standalone for `cargo publish` (the workspace path does not ship). A CI drift test fails if it diverges.

- To change the contract: edit the Zod schemas / contracts in `packages/shared`, run `npm run gen:openapi`, commit all three specs together (`openapi.json`, `openapi.codegen.json`, and the vendored `tui/openapi.codegen.json`). Never edit a spec or the generated `mod generated` by hand.
- progenitor needs **OpenAPI 3.0** and cannot model an operation with two distinct 2xx bodies. `openapi.codegen.json` is the truthful `openapi.json` minus such operations (`codegenExclude`). Those few endpoints are **hand-rolled** in `SottoClient` (e.g. `next_class` — 200 `{done}` vs 201 `{classId}`), as are multipart speaking uploads and `me`/`whoami` (multipart/identity that does not codegen cleanly).

## Auth & config

- Auth reuses the server's `sk_sotto_` API-key pairing: `sotto login` redeems a pairing code (from Settings → Devices) into a key. Config lives at `~/.config/sotto` (TOML): an `active` profile and a `profiles` map (`server_url`, `api_key`, optional `name`). Legacy single-credential configs migrate to `profiles.default`.
- The authed `http` client carries `Authorization: Bearer <key>`. The separate `download_http` client used for presigned/CDN segment audio carries **no** Authorization header — never leak `sk_sotto_` to a third-party host.

## Testing conventions

- Inject behavior through the `Api` trait: production uses `SottoClient`; tests use a `StubApi` returning canned results, so dispatch/reducer logic runs with zero network and no task-timing flakiness.
- Hand-rolled HTTP (multipart upload, `next_class`, `me`, speaking poll) is covered by loopback `TcpListener` tests that assert path/method/query/body/`Bearer`/parse. When you add or change a hand-rolled request, assert the bearer header and the request body, not just the path.
- Test the pure state machine directly; assert on resulting state, not on which method was called.

## DO / DON'T

- DO keep `app/state.rs` pure and side-effect-free.
- DO bump `request_gen` whenever you cancel or supersede in-flight work, so late results are dropped.
- DON'T edit `mod generated` or any `openapi*.json` by hand — regenerate from `packages/shared`.
- DON'T attach the Sotto key to downloads, or add business logic the server should own.
- DON'T name anything `gen` (reserved in edition 2024) — use `req_gen` and similar.
